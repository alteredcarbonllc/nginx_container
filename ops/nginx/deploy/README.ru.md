# Deploy локального образа NGINX

Это дополнение к уже установленным runit и local-transfer. Работает от root через установленную команду, исходники checkout не исполняются через sudo в CI. GHCR не используется. В GitHub изменения нужно закоммитить самостоятельно.

## Первый запуск

Из корня nginx_container на VPS:

```sh
sudo sh ops/nginx/deploy/install.sh
sudo /usr/local/sbin/ac-nginx-deploy --check 9371897acd9daa4b5a3557e5981234be3106ff4b
```

Этот SHA уже успешно импортирован в текущем сеансе. CHECK_OK подтверждает проверку образа по квитанции импорта, существующего nginx1, его сети/портов/mounts, HTTPS baseline и nginx -t нового образа с production-конфигом и сертификатами. Проверочный контейнер подключается к ac_network со свободным динамическим адресом, не публикует порты; конфиги, сертификаты и контент подключаются RO, каталог логов RW. Отдельная IP нужна для разрешения имён upstream в ac_network. SELinux enforcing не поддерживается этим вариантом.

После CHECK_OK можно выполнить первое переключение вручную:

```sh
sudo /usr/local/sbin/ac-nginx-deploy --deploy 9371897acd9daa4b5a3557e5981234be3106ff4b
```

Либо добавить шаг из woodpecker-step.yaml после import-local-image, закоммитить и отправить изменения. Тогда следующий успешный pipeline выполнит первое переключение автоматически. На время stop/start будет короткий перерыв обслуживания всех сайтов NGINX. Не добавляйте условия запуска шага после ошибки. Сохраните ограничение pipeline на main и push/manual; доступ к аккаунту ac-ci-builder должен быть только у доверенных репозиториев.

## Поведение

Команда разрешает только --check/--deploy и полный SHA. Читает root-owned квитанцию импорта и использует immutable image ID; запускает только заданный nginx1 с фиксированными host paths, IP, MAC и портами из ранее проверенной конфигурации. Перед изменениями проверяет текущую конфигурацию на расхождения. Одновременные вызовы исключаются flock.

После preflight сохраняется root-only журнал /var/lib/ac-nginx/deployments/<timestamp>-<token>.json. ac-nginxctl stop ставит down и ждёт остановки через runit с SIGQUIT. Прежний nginx1 переименовывается в nginx1-rollback-<timestamp>-<token>, затем создаётся новый nginx1 и запускается через ac-nginxctl start. Для сохранения прежнего контейнера используется podman rename; он освобождает имя для нового контейнера.

У нового контейнера restart=no; запуск и восстановление процесса выполняет runit. Проверка ждёт три HTTP 200 подряд от https://ci.belov.email/ с прямым подключением к 93.115.20.205 и проверкой TLS; между проверками контролирует, что контейнер не перезапустился. Проверяется конфигурация сети/портов/mounts нового контейнера. Остальные виртуальные хосты, IPv6 и UDP/HTTP3 этим health check не проверяются.

При ошибке переключения попытка отката выполняется автоматически: остановить supervisor-managed nginx1, удалить неудачный новый контейнер, вернуть имя прежнему и запустить его через runit; затем проверить HTTPS. Даже после успешного отката pipeline завершается ошибкой. Старый контейнер после успешного deploy остаётся остановленным для ручного отката; автоматической очистки старых контейнеров/образов пока нет. Не запускайте rollback-контейнеры одновременно с nginx1: адреса и порты одинаковые.

## Ограничения и диагностика

Механизм не меняет systemd/runit boot adapter и не требует systemd для deploy. root helper и supervisor устанавливаются администратором один раз; код из CI не обновляет root helper автоматически.

Образы доверенные: deploy запускает rootful image с рабочими данными и сертификатами. Sudo-доступ даётся аккаунту ac-ci-builder, а не отдельному репозиторию. Контроль SHA и метки не является криптографической проверкой происхождения.

Откат возвращает контейнер и образ, но не откатывает изменения в общих каталогах. Не обновляйте конфиги/сертификаты и не запускайте ручные start/stop одновременно с deploy. flock блокирует только другие вызовы ac-nginx-deploy. SIGTERM/SIGINT/SIGHUP запускают попытку отката; SIGKILL, потеря питания и сбой хоста её не гарантируют. После таких событий используйте root-only JSON-журнал и podman ps -a; не удаляйте прежний контейнер.

При ROLLBACK_FAILED сохраните вывод и журнал. Для ручного восстановления сначала выясните по журналу old_id и backup_name. Остановите ac-nginxctl, убедитесь что nginx1 (если существует) — именно неудачный новый контейнер, и только тогда удалите его, переименуйте old_id обратно в nginx1 и выполните ac-nginxctl start. Не используйте общий podman prune/rm -a.

Логи приложения остаются в прежнем bind mount, stdout/stderr — в /var/log/ac-nginx-supervisor/current и podman logs. Проверки кода без Podman выполнены локально; реальный --check и первое переключение нужно проверить на VPS.
