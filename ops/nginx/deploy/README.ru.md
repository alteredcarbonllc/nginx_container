# Деплой образа и конфигурации NGINX — v3 (config CI)

## Что изменилось

- `--deploy IMAGE_SHA` сохраняет mount конфигурации работающего nginx1.
- `--deploy-config CONFIG_SHA` сохраняет текущий образ, сверяя его с импортной квитанцией.
- `--check` и `--check-config` выполняют предварительные проверки без замены контейнера.
- Конфигурация — `/var/lib/ac-nginx/config-releases/SHA/nginx`, read-only.
- `migration-v1` остаётся допустимым исходным mount для первого перехода.
- Старый writable mount из containers_etc больше не допускается.
- Выпуск проверяется по полному набору SHA256 файлов source/nginx; ссылки и доступ на запись
  для group/other запрещены, владельцем должен быть root. Это контроль целостности и прав,
  а не цифровая подпись. Администратор всё ещё может изменить файлы и manifest.
- Проверки сайтов берутся из source/sites данного выпуска. Исполняемый проверяющий код
  устанавливается в /usr/local/libexec, код из выпуска с правами root не запускается.
- HTTP/3-клиент закрепляется по ID в /etc/ac/nginx-http3-image; pull во время деплоя запрещён.
- Два вида деплоя, prepare, installer и cleanup используют deployments/lock.
- CI ac-ci-builder может деплоить образы и подготовленные конфигурации.
  Отдельное sudoers-правило разрешает только prepare --import SHA, не root git checkout.

## Установка

Архив распаковывать из корня nginx_container. Сначала сохранить копию ops/nginx
и установленных /usr/local/sbin/ac-nginx-deploy и /usr/local/libexec/ac-nginx-verify-inspect.

    sudo sh ops/nginx/deploy/install.sh

Installer проверяет наличие локального ghcr.io/macbre/curl-http3:latest (при первом pin),
поддержку HTTP3, синтаксис Python и sudoers. Не меняет работающий контейнер.
Установка нескольких файлов не является атомарной при аварии питания: при прерывании
повторить installer до следующего деплоя. Перед копированием остановить запуск новых CI jobs;
не выполнять установку параллельно с началом деплоя. Блокировка защищает активную транзакцию.

## Первый переход

Уже подготовлен выпуск 5c82841793e72c9028a1016c568c04d8f1cce1b7:

    sudo ac-nginx-deploy --check-config 5c82841793e72c9028a1016c568c04d8f1cce1b7
    sudo ac-nginx-deploy --deploy-config 5c82841793e72c9028a1016c568c04d8f1cce1b7

`--check-config` проверяет целостность, текущие сайты (если текущий mount — SHA-выпуск),
HTTPS baseline и nginx -t кандидата. Не означает, что HTTP-запросы уже проверены на кандидате.
После замены контейнера выполняются проверки выбранного выпуска: обычные HTTP/HTTPS,
затем HTTP/3 через публичный IPv4 с VPS. Это не проверка внешнего маршрута или IPv6.

Для migration-v1 доступны baseline HTTPS и nginx -t; его старые проверки ранее выполнены вручную.
На новых SHA-выпусках выполняются полные проверки до и после изменения.
Одинаковая пара image/config не пересоздаёт контейнер, но проверяется.

## Следующие выпуски

    cd /root/git/nginx_config
    # commit / push / pull по обычному рабочему процессу
    git rev-parse HEAD
    sudo ac-nginx-config-prepare FULL_CONFIG_SHA
    sudo ac-nginx-deploy --check-config FULL_CONFIG_SHA
    sudo ac-nginx-deploy --deploy-config FULL_CONFIG_SHA

Prepare читает точный commit из локального Git, игнорирует незакоммиченные файлы,
строит выпуск доверенным установленным инструментом и выполняет nginx -t текущим образом.
Не выполняет git pull и не переключает production. Существующий выпуск не перезаписывает.
Не редактировать готовые выпуски: изменения делаются новым коммитом.

## Откат и очистка

Ошибка после начала замены вызывает возврат исходного контейнера, HTTPS-проверку,
проверку inspect и сайтов старого SHA-выпуска. Успех фиксируется фазой rolled_back,
сам неудавшийся деплой возвращает ненулевой код. При ROLLBACK_FAILED изучить журнал,
не запускать следующую миграцию вслепую. SIGKILL/потеря питания не обеспечивают автооткат.

Журнал сохраняет revision как SHA ОБРАЗА для совместимости с очисткой.
Дополнительно: operation, old_config, new_config, config_revision.
Очистка контейнеров/образов не изменена; сохраняет последние два доказанных rollback-контейнера.
Каталоги конфигураций НЕ удаляются автоматически. Сохраняются также source/checks для отката.
Для ручного возврата к ранее подготовленному SHA: --deploy-config PREVIOUS_CONFIG_SHA;
он проходит обычные проверки и сохраняет текущий образ.

## Проверки разработки

    python3 -m unittest discover -s ops/nginx/deploy/tests -v

Локально выполнены тесты транзакций с подменой Podman/runit: независимость image/config,
no-op, check-only, повреждение выпуска до stop, откат при ошибке сайтов.
Проверены хеши, лишние файлы, ссылки и совместимость журнала с cleanup.
Реальный Podman/NGINX в среде разработки недоступен: интеграционная проверка выполняется на VPS.

## Ограничения

Это фиксированный host deployment. IP/mount/порты остаются привязаны к данному VPS.
Проверки обращаются к рабочим сайтам и БД; они не создают отдельную копию WordPress.
При первой миграции listen.allowed_clients PHP-FPM менять не требуется: IP nginx остаётся .224.
Одновременное ручное редактирование выпусков/контейнеров вне общей блокировки не поддерживается.
Health baseline ci.belov.email пока остаётся отдельным инфраструктурным условием.

## Woodpecker для nginx_config

Сначала установить поддержку: sudo sh ops/nginx/deploy/install-config-ci.sh.
Она вызывает обычный installer, создаёт config-inbox (UID 1001, mode 0700),
добавляет sudoers для prepare --import. Контейнер не переключает.
Затем добавить .woodpecker.yaml и ci/export-config.sh в nginx_config и активировать
репозиторий в Woodpecker. Backend local, события push/manual, ветка main.

CI проверяет структуру как UID 1001, экспортирует точный Git commit в tar, атомарно
публикует /var/spool/ac-nginx/config-inbox/SHA.tar. Root копирует файл в закрытый staging,
проверяет тип, размер, пути и отсутствие ссылок; не выполняет исходные скрипты.
Выпуск строится установленным ac-nginx-config-tools и проходит nginx -t.
Далее --deploy-config выполняет существующие проверки и откат.

Ограничения доверия: SHA здесь — идентификатор заявленного CI коммита, не доказательство
его происхождения. Импортер не проверяет подпись Git или GitHub. Как и существующий
импорт образов, он доверяет ac-ci-builder. Все задания с этим host UID разделяют его
права. Конфигурация nginx является привилегированным содержимым; проверки архива
не превращают произвольную конфигурацию в безопасную. Доступ к main и local runner
должен оставаться у доверенных участников. Этот пакет не создаёт изоляцию по репозиториям.

Повторный импорт того же SHA сравнивает весь набор исходных файлов и их хеши;
другие исходники под тем же SHA не перезаписывают выпуск.
Готовые выпуски и inbox автоматически не чистятся. CI не меняет /root/git/nginx_config:
его git pull нужен только для ручной работы администратора.

Если image/config pipeline столкнутся на блокировке, один завершится ошибкой без изменения
production. Повторить его после завершения другого. Не запускать старый manual pipeline,
если нужен последний main: ручной запуск конкретного старого SHA означает откат к нему.
Для первого запуска можно вручную запустить pipeline последнего main после активации репозитория.

Локально: 16 тестов (10 регрессионных + 6 импортера), синтаксис Python/shell/YAML.
Реальный первый CI импорт/деплой проверяется на VPS.
