# Очистка конфигураций и inbox

Установка: sudo sh ops/nginx/cleanup/install-config-cleanup.sh.
Не переключает контейнеры. Сохраняет копию установленных cleanup-скриптов в
/var/lib/ac-nginx/cleanup-install.*. Исходники устанавливать через обычный Git-процесс.

Предварительный просмотр:

    sudo ac-nginx-config-cleanup

Применение того же алгоритма с новым чтением состояния:

    sudo ac-nginx-config-cleanup --apply

При установке впервые автоматическая очистка НЕ включена. После просмотра dry-run:

    sudo install -o root -g root -m 0600 /dev/null /var/lib/ac-nginx/config-cleanup-enabled

Теперь существующий ac-nginx-cleanup вызывает конфигурационную очистку после освобождения
своих блокировок. --apply передаётся дальше; без --apply обе очистки работают как dry-run.
Деплой уже вызывает ac-nginx-cleanup --apply после успеха, включая no-op.
Новых cron-задач нет. Ошибка cleanup остаётся предупреждением деплоя.
Отключение: sudo rm /var/lib/ac-nginx/config-cleanup-enabled.
Переустановка сохраняет текущее состояние флага, а не выключает его.

Правила:
- Работающий nginx1 обязателен. Любой незавершённый журнал останавливает очистку.
- Все контейнеры проверяются, не только nginx1. Остановленные контейнеры тоже защищают
  свои bind mounts; защищаются также parent/subdirectory mounts выпуска.
- Сохраняются два последних успешно применённых config SHA независимо от контейнеров.
- Требуется healthy-журнал с точным new_config и config_revision, более новый, чем выпуск.
  rolled_back не доказывает успешное применение кандидата. Старые журналы без config полей
  не используются как доказательство удаления.
- migration-v1, staging, неизвестные имена и неподтверждённые выпуски не удаляются.
- Минимальный возраст выпуска/архива — 24 часа.
- Хеши и набор файлов выпуска должны совпадать с root-owned manifest.
- Архив inbox удаляется только при полном совпадении его файлов с source выпуска и healthy
  позже mtime архива. Более новая загрузка сохраняется. Даже при no-op после повторной загрузки
  без нового healthy-журнала архив может сохраняться дольше — это консервативное поведение.
- Перед удалением архив перемещается в закрытый root-каталог quarantine и снова проверяется.
  Если его успели заменить, он возвращается без перезаписи более нового файла. При конфликте
  остаётся в quarantine с явным сообщением. Этот каталог автоматически не очищается; после
  аварии он может содержать сохранённый архив, который надо разобрать вручную.
- Если обнаружен изменившийся архив, выполнение прекращается; уже завершённые удаления
  не откатываются. APPLY_OK выводится только при завершении всего прохода.
- Перед удалением выпуска повторно проверяются контейнеры и наличие inbox-архива.
  Общая deployment-блокировка исключает одновременный импорт/деплой. Прямые ручные изменения
  контейнеров/каталогов вне блокировки не поддерживаются. CI-публикация архива идёт отдельно:
  если она совпадёт с удалением уже ненужного выпуска, новый архив сохраняется, а следующий
  импорт вновь соберёт выпуск. Это не гарантия изоляции от произвольных действий ac-ci-builder.

Данные сайта, сертификаты, Git-репозитории, журналы деплоя, images/import receipts не удаляются
этим скриптом. Существующая политика контейнеров/образов не изменена.

Проверки:

    python3 -m unittest discover -s ops/nginx/cleanup/tests -v

14 локальных тестов покрывают правила удержания, совпадение архива, ссылки, замену архива,
восстановление без перезаписи. Проверены синтаксис Python и shell.
Podman локально не запускался; первый реальный dry-run выполняется на VPS.
